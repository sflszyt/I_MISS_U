## 〇、直接回答"GitHub 有没有开源"

**有零件，没成品。** 没有任何开源项目开箱即用地在你的 **Weixin.exe 4.1.12.26** 上做到"OCR 读消息 + 发文字 + 发她的真声"——只散落成零件，得自拼且脆。而**你在社媒看到的那种"skill"，最像的是 UIA 路线的两个项目，恰恰在你的版本上是死的**：

- **LeoMusk/wechat-rpa-bot-skill（YoKo，~83★）**：唯一"带语音+MCP+开箱"的"skill"（27 个 MCP 工具、专为 AI 智能体设计，最匹配你说的"skills"）。**但它走系统原生 UI 自动化（不是 OCR）+ 闭源 exe**，是任务 #16 §3 商用 YoBot 的开源壳——YoBot 版本止步 4.1.9，其对 4.1.12.26 无任何可用证据。
- **Hello-Mr-Crab/pywechat（~1874★，活跃）**：近乎一体化（监听收消息+发文字+`send_audios_to_friend` 发真语音条，需 ≥4.1.9+虚拟声卡）。**但同样是 UIAutomation**，194 个 open issue、在 4.1.6/4.1.8.x 多版报障，4.1.12.26 未见实证。

**而 UIA 在你的 4.1.12.26 上已被任务 #16 活体探针铁证判死**（控件树恒 3 节点空壳、五重触发全败）。所以这些"skill"的语音能力对你**无效**——它们依赖的无障碍树在你版本上被腾讯主动关掉了。

## 二、本机可行性：一个重要新事实 + 一堆脆点

### ★ 新事实（校核 confirmed，多源实证）：微信 PC 4.1.9 起支持发原生语音条

微信 Windows/Mac **4.1.9（2026-04-22 发布）首次支持电脑端发语音消息**，麦克风按钮提示"发送语音（按住 **右Alt**）"，单条上限 60s，松手即发。**你的 4.1.12.26 已具备此能力。** 这**实质更新了我们之前"PC 只能把她的声音当文件发"的结论**（dsh-im 报告 / messaging-channels）。

因为录音绑在**键盘快捷键**（右Alt）上，可用 `keyDown/keyUp('altright')` 自动化，**不用坐标点那个按钮**——配 **VB-Cable 虚拟声卡**把她的 CosyVoice TTS（:8022 出 MP3）灌进"微信的麦克风"，就能发出**原生语音条**（虚拟线做输入还顺带消除环境噪声）。**这是四条微信路径里唯一能把她真声送成家人聊天里原生语音条的路。**

**但两个诚实风险**：①微信语音管线是低码率单声道 + AGC/降噪，**很可能劣化她的克隆音色**——正是 M1 盲听关口保住的东西，须活体 A/B；②松手即发/预览 UX、虚拟麦是否被接受，须动工前活体核验。

### 脆点（这条链先天脆，"最脆一层"实锤）

- **读侧**：微信 4.x Qt 自绘无控件树，只能截图+OCR（wxocr.dll）；定位气泡靠固定坐标/截图差分（现成开源做法都很粗糙）。**DPI/主题/字号/窗口位置四重敏感**；窗口被遮挡/最小化/移动即瞎；纯轮询无事件信号（1-3s 截屏比对）；微信强制自动更新随时改布局。
- **发文字**：剪贴板+Ctrl+V+Enter 是全链**最稳一环**。
- **收语音**：微信自带转文字**只认普/英/粤，不认上海话**——家人说沪语转写会错或空；要听懂沪语得绕回抓音频文件喂本机 ASR（SenseVoice，吴语 CER ~20%），这已超出"纯 OCR"能力。

### 校核翻案：OCR 不是"唯一绕开 UIA 的路"（refuted）

对抗校核用**我们自己的文档**推翻了这条：wechat-ui-automation.md 第六节早已列出两条非 UIA 退路——**读=解密本地 DB 轮询**（不碰进程/不读控件/不读像素，是首选读侧）、发=坐标级 PyAutoGUI 或 OCR。所以真要做，正解是**"DB 读 + 坐标/OCR 发 + VB-Cable 语音"的混合**，OCR 只是发送侧的脆弱选项之一，不是读侧主力。

## 三、封号与伦理

**封号（校核 confirmed）**：OCR+模拟键鼠不注入进程、不伪造协议，是第三方方案里**客户端封号风险最低的一档**（社区共识：协议/Hook >80%，RPA/视觉远低）。但它只是把风险从"客户端注入检测"搬到"**服务端行为模型**"（高频/秒回/24h/内容重复/新号权重照旧生效），**绝非隐身**。本项目"永不主动+被动+低频"几乎清空全部触发器，残余=新号权重（养号缓解）+违 ToS（后果=可弃小号被封的合同处置，非法律责任）。**绝不用逝者原号/主号，用专用可弃小号。**

**伦理（校核对照 #20，这条比 iLink 更该保守）**：这仍是"把妈妈接入真微信与人聊天"，**家人向 = 默认 NO-GO**（第三方受众、沉浸/欺骗最大化、griefbot 三方同意共识、2025 有团队拒绝把逝母微信记录做数字分身的逐字同构先例）。**OCR 独有的伦理放大点**：iLink 天然带 bot 标识 + 家人扫码知情添加——欺骗被官方标识兜了底；**OCR 却劫持一个"看起来完全是普通真人在用"的微信账号，零标识，对方察觉门槛最高、欺骗性最强**，直撞"必须明确标注为模拟"的学界共识与"沉浸度是唯一要克制的指标"铁律。而它唯一的技术加分（能发原生语音条=冒真度最高）恰恰是伦理加压。

## 四、四路径对照（校核修正版）

| 路径 | 技术（你的 4.1.12.26） | 发她真声语音条 | 家人向裁决 |
|---|---|---|---|
| ① UIA 自动化（#16） | **NO-GO**（控件树空壳，读发归零） | pywechat 声称可但 UIA 死 | 技术已死 |
| ② iLink 官方协议（#20） | 官方但"官方≠可给家人用" | **不能**（协议无 sendVoice） | 默认 NO-GO |
| ③ 服务号/企微 | 需企业主体；企微拦外部个人微信 | — | NO-GO |
| ④ **OCR/RPA（本路）** | 可行但**最脆**；正解=DB读+坐标/OCR发 | **能**（4.1.9+ 右Alt+虚拟声卡，音色待验） | **默认 NO-GO，且比 iLink 更甚**（零 bot 标识、欺骗性最强） |

**校核 refuted 了"OCR 独占家人可达格子"**：iLink 扫码同样家人可达，它被排除是靠伦理否决而非技术——同一伦理否决同样压在 OCR 上。**没有一条微信路径为"家人向"打开了干净的门。**

## 五、接入设计（若仅自用验证）

OCR 路接我们的资产：**三块现成、一块全新、且大脑要移植**。
- **现成**：她的声音 :8022（tts_server.py 零改）、VB-Cable 驱动、SenseVoice 模型、BYOK LLM 端点、pilk（SILK 编解码）。
- **要移植**：**大脑现在只活在 chat.html 的浏览器 JS 里**（三源检索/Tier 标签/BYOK/SSE 全在前端，tools/ 无 Python 运行时检索器）。任何 headless 皮肤（TG/iLink/OCR 微信）都要把这批纯函数**直译成共享的 `persona_core.py`**——避免 JS/Python 双实现漂移。这与 messaging-channels 的"persona 引擎 Python 移植"是同一件事，companion 仍走浏览器皮肤，两者共享数据文件+chat_system.zh.md+:8022+未来 ASR 服务，而非同一进程。
- **全新且最脆**：把她的声音发成原生语音条的 VB-Cable 录音编舞（开始录音→精确时长播放→松手发送，与不透明 UI 实时编舞，DPI/窗口敏感）。

**数据不出机的精确澄清**：任何"进真微信"方案，消息本就全程过腾讯（微信无端到端加密）——OCR 只是读**已投递到你屏幕上**的消息，不新增对腾讯的服务器关系；离开本机的只有当轮对话文本 + BYOK LLM 调用。**people/ 档案两种路径都不上传。**

## 六、裁决与建议

**技术**：OCR/RPA 是四路径里唯一"技术可行 + 不碰协议 + 能发她真声语音条"三者可凑齐的路，但代价是**最脆链路 + 长期维护地狱**（微信强制自动更新随时打断），且没有现成开源可套（你社媒看到的"skill"是 UIA 路线，在你版本上死）。

**伦理（决定性）**：**自用**（绑你自己的号、仅自测、顺带落地轴五 sessions 采集）= 有条件 GO / 低风险——但自用场景 **TG bot / iLink 自用比脆弱的 OCR 坐标层更干净**。**家人向 = 默认 NO-GO，且因"零 bot 标识、欺骗性最强、能发冒真度最高的语音条"应比 iLink（#20）更保守。**

**给用户的一句话**：你在社媒看到的"OCR 控微信聊天 skill"是真的存在（YoKo/pywechat 那类），但①它们大多是 UIA 不是 OCR，在你的 4.1.12.26 上是死的；②真做得靠"DB 读 + 坐标发 + 虚拟声卡"混合自拼；③最关键的不是能不能做，而是**它是所有微信路径里最难让家人察觉在跟"模拟妈妈"聊的一条**——技术门开了缝，决策仍落在伦理面。
