# 研究：微信 UI 自动化部署数字人可行性（wechat-ui-automation）

> 2026-08-22 立项（任务 #16）。问题：能否登录一个专用微信【小号】，在家用 PC 上通过【UI 自动化/模拟操作电脑打字】的方式，让"数字妈妈"在微信聊天里回复家人？
> 方法：workflow 5 代理并行核证（4 维 + 1 生死题独立复核），97 次网络检索，2026-08 现状。
> **区别于 messaging-channels.md 已否决的路线**：那里否决的是"个人号机器人 = hook 进程/iPad 协议伪造"。本研究是真客户端真登录 + Windows UIAutomation 读消息 + 剪贴板/键盘发送，无注入无协议伪造，行为上=人在操作电脑。

---

## 一、生死题裁决：技术可行（is_viable = TRUE），但卡一道闸门

**结论：可行，但不是"pip 装个库就能跑"。** 新版微信 4.x 不是黑盒，但默认对自动化"装死"——必须先骗它"有无障碍软件在用"，UI 控件树才会长出来。这道闸门是整条路线唯一的致命单点。

### 关键现场事实
- 用户本机 = **Weixin.exe 4.1.12.26**（新架构，非旧 WeChat.exe 3.9.x）。微信 Windows 最新已到 4.1.13.10（2026-08-21）。
- 本机主进程当前未运行，且无 UI 自动化库——**活体 UI 树探针尚未做**（见第五节 go/no-go）。

---

## 二、为什么"成熟工具全废，但路线仍通"

### 2.1 架构变了（根因）
微信 4.0 起从 Win32/Qt Widgets 原生控件改为 **Qt Quick/QML + C++ 自绘跨平台框架**（腾讯官方《微信 PC 版 4.0：新架构》）。绝大多数控件不再有独立 HWND，界面直接画在画布上。这是腾讯**主动的反自动化措施**。

### 2.2 但不是真黑盒——"按需暴露"
决定性发现：4.0.3+（约 4.1.5.16 定型）改为**按需暴露**——
- 默认：UIAutomation 只看到 1-2 个骨架节点（inspect.exe 被动看=空壳窗口，"UI 树消失"的来源）。
- **一旦检测到无障碍客户端接入**（启动"讲述人"，或让一个持续运行的 uiautomation/pywinauto 客户端主动 attach 并遍历），**完整控件树会"长出来"**——消息文本、联系人列表、输入框、按钮全部可读可操作。
- 注意：光 import 库不够，必须**主动建立连接并遍历**（库本身就是那个"无障碍客户端"）。Qt 在 Windows 上只经 QAccessible→UIA bridge 暴露，没有 MSAA 后门；读不到时唯一兜底是 OCR。

### 2.3 工具支持矩阵（2026-08）
| 工具 | 支持版本 | 对本项目（4.1.12.26） |
|---|---|---|
| wxauto 开源版（cluic，7.3k★） | 仅 3.9.x，2025-10 停维护 | ❌ 不适用 |
| wxautox 付费（3.9 线） | 3.9.8+ | ❌ |
| wxautox4 付费 Beta | **仅 4.0.5** | ❌ |
| cluic/wxauto4 开源 | 4.0，已"停止更新" | ❌ |
| **pyweixin**（Hello-Mr-Crab/pywechat，1.9k★，pywinauto） | 声明 4.1.6+/≥4.1.9，读+发均具备 | 🔶 **主选候选**，但未确认 4.1.12 |
| wx4py（claw-codes，725★） | 实测 4.1.7.59/4.1.8.29 | 🔶 备选，读消息+监听 |
| wxrpa（wymliuming，46★） | 4.1.1–4.1.8.29，收发皆可 | 🔶 参考"激活 UI 树"实现 |
| LAVARONG/wechat-automation-api（168★） | 4.0+，**仅发送不读** | 🔶 send-only，有 4.1.x 碎裂 issue |

**版本追逐是最大工程风险**：用户 4.1.12.26 比任何库公开实测过的最高版本（4.1.8.29/4.1.9.35）还新 3-4 个小版本。底层 Qt 无障碍激活机制与小版本无关（原则上仍能读），但各库硬编码的控件定位会随小版本更新失效，且微信强制自动更新会随时打断。

## 三、替代方案（UIA 激活不出来时的退路）

按对本项目的现实度排序：

1. **混合方案（最优退路）**：读=解密本地 DB 轮询新消息（结构化、可靠、不碰微信进程；用户已在 4.1.11 用 chatlog-keeper 取过 key），发=UI/剪贴板自动化。**把脆弱点只锁在"发送一步"**。
   - 读库注意：旗舰 sjzar/chatlog 已于 2025-10 因法律原因删库；活跃替代 = LifeArchiveProject/WeChatDataAnalysis（2.3k★，微信 4.x，key_v4 + 实时消息同步 + API :10392 + MCP）。
2. **微信自带 OCR（wxocr.dll）+ Win32 剪贴板发送**：swigger/wechat-ocr（961★，支持 4.0，离线免费，优于 Tesseract/PaddleOCR）。读像素不读控件，绕开 DirectUI。缺点：坐标/DPI/分辨率敏感。
3. **纯 PyAutoGUI + OCR 全链路**：可行但最脆（现成项目都很小、自述"不稳定"）。
4. **商用 RPA**：YoBot（yokoagi.com，非 hook、人工复核、频率约束、REST——**理念最贴合本项目**，但收费且版本止步 4.1.9）；影刀/Quicker 有 4.0+ 视觉方案文档。

## 四、风控与法律（对本项目=低但非零）

### 风控
- UI 自动化封号风险**显著低于**协议/Hook（后者封号率 >80%），2025-2026 社区共识。但"零封号"是厂商营销话术——**所有第三方自动化都违反微信 ToS**，后果=该小号被封（合同处置，非法律责任）。
- 本项目"**永不主动 + 只被动回复家人 + 低频**"避开了几乎所有封号触发器（主动加人/群发/营销/投诉）——风险画像极有利。
- 两个残余风险：
  1. **新小号权重低**（新号 30 天风控重点期）→ 对策：先人工实名 + 养号 14-30 天（完善资料、发朋友圈、绑卡小额支付、当活人号用）再上自动化。因永不主动加好友，最大触发器已消除。
  2. **"唤起无障碍树"这个动作本身**是新的、未被大规模实测的指纹暴露面。
- **绝不用逝者原号，也绝不用高价值老号**——用专用可弃新号，把小号当"可承受完全损失"的一次性资产（封号只损失通道，档案/persona/TTS 全在本地）。

### 法律（家庭私用非公开场景）
- 大概率**不落入**《生成式 AI 暂行办法》（第 2 条：未向境内公众提供服务的不适用）与《深度合成规定》（义务主体是"服务提供者"）的监管射程。
- 逝者数据处理有 PIPL 第 49 条基础（近亲属为自身合法正当利益可处理）；法律界主流认为"寄托哀思范围内的 AI 复活具合理性"。红线是对外传播/商用/诈骗/侵害肖像声音权——本项目均不触及。
- ToS 补充：微信禁止"未经其他用户明确同意复制/存储其数据"——**采集家人聊天需家人知情同意**。

## 五、落地路线与 go/no-go 探针

### 判定闸门（30 分钟探针，动工前必做）
在**弃用小号**上、精确停在 4.1.12.26 且关闭自动更新：
1. 启动微信 → 用 uiautomation/pywinauto 起一个常驻客户端主动 attach 遍历（讲述人 Win+Ctrl+Enter 作兜底）→ 打开 inspect.exe，**肉眼确认消息列表文本与输入框是否在控件树里"长出来"**。
2. **长出来 = 整条路线 GO** → `pip install pyweixin`，用 Monitor 测读、向文件传输助手测发。
3. **仍是空壳 = 降级混合方案**（DB 轮询读 + UIA/剪贴板发，读侧不依赖 UIA）。

### 若 GO，落地形态
- 复用 messaging-channels.md 的**通道网关架构**——微信只是又一个 channel adapter：persona 引擎（chat.html 检索逻辑 Python 移植）+ LLM(BYOK) + TTS(:8022) + sessions 写回（轴五基建）。
- 铁律不变：代码 DeepSeek 写 + Codex 审；永不主动发消息；小号标注"数字档案·非本人"；家人知情同意。
- 运维预期：**调通后锁版本、关自动更新**；把"每次微信升级需用 inspect 重新定位控件"写进预期。

### killer_risk（最可能让路线失败的单点）
"按需无障碍暴露"这道闸门的检测逻辑是腾讯私有、作者们明说"无法 100% 保证"，且 4.1.10-4.1.13 无人公开实测——若该启发式在 4.1.12.26 上被收紧，附加 UIA 客户端 + 讲述人都唤不出树，则**读与发同时归零**。次级：控件标识小版本漂移、强制更新推到未验证版本。→ 正因如此，探针（第五节）是动工前的硬闸门，且混合方案（DB 读）是这道单点失败时的保命退路。
