# 桌面陪伴型数字人可行性研究（任务 #18）

> 立项：2026-08-27 用户指令"研究是否可以构建桌面陪伴型数字人，用户利用打字或语音与他/她进行交互，她返回语音或文本"。
> 方法：多代理研究 workflow——6 个维度并行调研（本仓资产 / 桌面壳 / 语音闭环 / 对话层 / 先例 / 伦理约束）+ 8 条载重论断对抗校核（6 confirmed / 2 refuted，含 4 组本机实测探针）。
> 结论性质：技术判断为工程事实；**"该不该做"的最终裁决属用户闸门**，本报告只给出诚实评估。

---

## 〇、一句话结论

**技术上完全可行，且是拼装级工程而非研发**——三大积木（她的声音 :8022 / 贴片口型 avatar 运行时 / BYOK 检索对话）全部已在仓库，缺的只是一张合流页和一个窗口壳；**但伦理评估的结论是：不应该做"常驻桌宠"，可做的上限形态是"打开才在的档案对话窗口"，且"维持现状不做"是完全合理的默认答案。** 沉浸度是本项目唯一需要克制的指标，而"常驻"这个属性本身，是文献共识与本项目铁律共同反对的东西。

## 一、技术可行性：积木全在，缺口是合流

### 1.1 已有资产盘点（校核 confirmed，逐文件核实）

| 积木 | 现状 | 复用度 |
|---|---|---|
| **她的声音** `tools/tts_server.py` :8022 | POST /tts（JSON→整段 MP3），CORS 全开，沪语/沪普双语域，≤120 字，内置时长 QC+解码回读自检；当前 `stream=False` | 高：零改动可调 |
| **会动的脸** avatar.html patch 运行时 | 恒定底图+四态嘴+眨眼+微摆；驱动优先级=viseme 时间轴 > WebAudio RMS 回退 > closed；纯 HTML+JS+PNG | 高：任何 webview 能跑 |
| **会说话的她** chat.html | 三源检索（Tier-1 记忆/Tier-2 转写/消息）+ 23.9k 字符 system prompt + SSE 双协议（OpenAI 兼容/Anthropic 直连）+ **≤120 字自动 TTS 语音条分支已实装** | 高 |
| **人格与安全约束** chat_system.zh.md | 六铁律内建（只说档案有的/记不清就说/Tier 纪律/保留缺点/不假装真人/**克制依赖禁挽留语**） | 高：零改动继承 |
| **精确口型** build_visemes.py + Rhubarb | 构建端批处理；本机实测 5.8s 音频仅耗 1.09s → "合成完先跑 Rhubarb 再播"可作准实时高保真档 | 中 |
| **ASR** venvs/asr（SenseVoiceSmall） | CPU 0.1-0.4s/条（实测）；但现状是批式 QC 工具，无麦克风链路、无 HTTP 服务 | 低-中 |

### 1.2 关键衔接点（校核 confirmed，代码级核实）

**"动态合成语音走 RMS 口型"= 分支在、音源没接。** avatar.html 对查不到时间轴的音频自动落入 WebAudio RMS 分支（这正是渲染研究 Phase 1 第 7 条预留给 BYOK 动态 TTS 的路径）；chat.html 的 TTS 语音条却用独立 `new Audio()` 播放、不驱动嘴；两页各持一半。**把 :8022 返回的 MP3 blob 设为挂 analyser 的 `<audio>` 的 src 即通全套口型+bob**——拼装级衔接，无新能力需求。

### 1.3 缺口清单（全部为工程项，无研究项）

1. **合流页** companion.html = avatar 贴片块 + chat.html 检索/双协议/TTS 分支 + blob 接口型（需先把 build_avatar_page 模板里约 800 行运行时 JS 抽成可复用模块）
2. **窗口壳**（见第二节，轨 0 甚至零代码）
3. **语音输入**：麦克风采集 + VAD + ASR HTTP 包装（仿 tts_server.py 模式）——建议后置第二阶段
4. **运维**：所有服务现全手动拉起；若做窗口形态也**刻意不做开机自启**（见第五节，这是伦理设计而非缺陷）

## 二、桌面壳选型：两轨结论

**架构总前提（校核 confirmed）：壳只当窗，永不打包档案。** 壳=指向 `http://127.0.0.1:8020/` 的窗口；壳死只失去桌面形态，档案与浏览器访问方式原样存活——把"壳会不会死"从否决项降级为便利性权衡。通信层零障碍：127.0.0.1 是 secure context（getUserMedia 可用），tts_server 已发 `Access-Control-Allow-Origin:*`。

| 路径 | 判定 | 要点 |
|---|---|---|
| **轨 0：Edge `--app` 模式** | ✅ 验证版首选 | `msedge --app=http://127.0.0.1:8020/companion.html` + PowerToys Always On Top；零代码零依赖零 20 年风险；矩形无透明 |
| **轨 1：Tauri v2** | ✅ 正式形态首选 | 透明/置顶/无边框/托盘/自启插件全官方，MIT/Apache-2.0，实战约 14MB RAM；已知坑（透明窗初始白闪 #10318、置顶拖拽性能 #7328）有绕法，交付按 verify-rendered-pixels 铁律做像素级验收 |
| Electron | 后备 | 功能等价但透明无边框窗 2025 年仍有活跃回归 bug 长尾，体积/内存大一个量级 |
| 原生 WebView2 宿主 | 备选 | 最少依赖但托盘/自启/穿透全手写；WPF 透明有 hit-test 已知 bug |
| PWA / Document PiP | ✕ | 无置顶无透明 |
| Wallpaper Engine / Lively | ✕ | 层级在桌面图标后、键盘输入不达，且 WE 是 Steam DRM 专有 |

注意：Chromium 系 autoplay 策略会拦无手势音频，各壳均需 `--autoplay-policy=no-user-gesture-required`（或保持点击触发型交互，短期可不处理）。

## 三、语音闭环与延迟预算（含本机实测）

**量级结论：准实时（她开口前 2.5-8 秒），不是电话级实时——且延迟本身是克制沉浸度的天然闸门，明确不追打断式实时。**

本机实测（研究+校核两轮独立复测，fp32 无优化）：

| 环节 | 实测 |
|---|---|
| Silero VAD | <1ms/块（0.048ms 复测）；真时延来自尾静音判定 0.3-0.8s（配置项） |
| SenseVoiceSmall ASR | CPU 0.1-0.4s/条（整段一击，10s 音频约 0.37s） |
| CosyVoice2 现役 SFT 非流式 | 5.07-5.62s 合成 7.8s 音频 |
| CosyVoice2 `stream=True` | **首包 2.18-4.44s**（本机代码原生支持，tts_server 只差改参数+HTTP chunked；方差大） |
| GPT-SoVITS api_v2 `streaming_mode` | **首包约 1.07s**（普通话臂声线的"快嘴档"） |
| Rhubarb（准实时口型） | 5.8s 音频 1.09s / 18s 音频 1.36s——"合成完先跑再播"仅加约 1 秒余 |

端到端估算：文本输入→上海话语音回复约 3.5-7s（CosyVoice 流式 + LLM 句级流水）；语音输入再加 0.5-1.2s；普通话回复走 GSV 流式可压到约 1.5-3s。口型两档并存：流式=RMS 分支（资产零新增），非流式=Rhubarb 时间轴（高保真）。

**上海话 ASR（校核 refuted 后修正）**：原研究判"本地开箱可用不存在"——**被校核证伪**。DataoceanAI+清华开源的 **Dolphin**（2025-03，pip 可装、权重 HF/ModelScope 公开、本地推理）语言表明确含 zh-WU 与 zh-SHANGHAI；厂方论文报 0.4B 模型上海话 CER 7.81%（对照 SenseVoice-S 吴语 20.43%），另有含流式的 Dolphin-CN-Dialect 专项。**数字出自厂方论文，对她/用户实际口音效果需自测**；SenseVoice 普通话主路径仍是稳妥起点，Dolphin 是值得一试的上海话输入候选（这也顺带是"她的语音转写校对负担"的潜在减负工具，超出本任务范围）。

## 四、对话层：BYOK 云端主线（校核后修正版）

- **默认 DeepSeek V4 Flash**，但有两处校核修正：①裸 `deepseek-v4-flash` **默认开思考**，首 content token 实测 4.69s——请求体必须加 `thinking:{"type":"disabled"}`（实测后 1.68s），而 chat.html 当前 payload 硬编码无此项=**一行改动**，顺带把已退役的 `deepseek-chat` 占位符刷新；②首 token 实测约 1.7s 而非 1s。成本量级 $1-3/月（谷段+前缀缓存，40 轮/天估）。
- Claude 线（Haiku 约 $5-8/月、Sonnet 约 $10-20/月）作可选高质量档；大陆访问需代理是日常摩擦。
- **本地 LLM（校核 refuted 后修正）**：原论断"与 TTS 共存只剩 8-14B 且小模型必违 Tier 纪律"推理链不成立——CosyVoice2 量化后占用可压很低、27B/30B-A3B Q4 可能挤入 24GB；且 Vectara HHEM 榜显示体量不决定检索忠实度（Phi-4 14B 优于 Llama-3.3-70B）。修正后定位：**本地线可行性高于原判，但 MVP 仍先 BYOK**（零新开发、质量上限高）；本地 llama.cpp OpenAI 兼容端点随时可作断网档接入，chat 层零改动。
- 供应商漂移风险已被实证（deepseek-chat 别名 15 个月退役）也已被架构消化（BYOK 可配置端点）。
- **写回铁线：mem0/Letta 式自动记忆库 = 本项目反模式**（模型自主决定"什么是事实"正是 Tier-3 闸门禁止的通道）。沿用 GENERALIZATION.md 轴五已定设计：sessions 原文 JSONL 存档、数字人话语永久 Tier-3、"记下来"→闸门页人工裁决。外部研究（memorywire 的 diff+人工审批、"逐字对话块优于抽取记忆"对照实验）反向验证了轴五设计。

## 六、伦理评估：这是本报告真正的裁决轴

### 6.1 证据

1. **arXiv 2603.01017（项目自引的立律研究）细读**：理想化是用户**主动共建**的（选择性喂料/对话调校/想象补全），并随时间演进为"AI 生成的新记忆与真实回忆模糊"。漂移速率与交互量正相关——**常驻等于把该机制开到最大档**。
2. **MIT Media Lab × OpenAI 2025**（400 万对话 + 981 人对照试验）：日使用时长与孤独感、依赖、社交下降正相关。"常驻桌面"这一形态的产品逻辑（降启动成本、增瞥见次数、ambient 在场）恰恰是制造高日时长的机器。
3. **Replika ERP 事件 + Soulmate 停服研究**："我知道它是 bot"不构成心理护栏——知情用户照样形成深度依恋，中断时经历等同真实丧失的哀伤。**"我是开发者我知情"不是自我豁免理由**；对丧亲者，未来任何中断（硬件故障/模型腐烂/自己停用）都是二次丧失，依赖越深创伤越大。
4. **学界唯一接近共识的安全定位**（Bao & Zeng 2024 等）：deathbot = **transitory use**——用户发起、有场景、有始有终的临时哀悼工具，**不是持续沟通模式**。Cambridge 2024 设计安全清单明确反对 deadbot 拥有 active presence。"常驻桌面"在结构上与这条边界正面冲突，也与本项目已定红线（GENERALIZATION.md：不主动发消息）相撞。
5. **本项目的结构优势是真实的**：无商业动机、全本地、Tier 纪律与"不假装真人"提示词已内建——对冲了文献中大部分**外源性**风险。但**内源性**风险（理想化/依赖/现实替代）只与交互频率和拟真度有关，而"常驻"恰好只提升这两样。

### 6.2 三档判定

**① 不应该做**：always-on 常驻桌宠、系统托盘、开机自启、主动搭话、系统通知、"她在等你"式空闲暗示。任何护栏救不回"永远在场"这个属性本身。

**② 有条件可做的上限形态："打开才在的档案对话窗口"**（桌面快捷方式/app 模式窗，复用合流页），条件全部满足才开工：
- (a) 她只应答不发起，无任何主动性通道；
- (b) 打开才在：关窗触发一句她真实风格的道别语（取自她真实语料的告别习惯，Tier-2），长时间空闲她自己"去忙了"——她生前本就不是随叫随到的人，**永远待机等你的妈妈是失真**（铁律 2"保留完整性"的直接应用）;
- (c) 每条回复的 Tier 出处与"合成语音·非原声"标签可见性**不得低于现有 chat.html**；
- (d) 遵守 rhythm.json 真实节律（她凌晨不回、做饭时慢回）——用她的真实节律做天然反依赖阀；
- (e) 使用统计在档案首页自见（不设硬锁——唯一用户是开发者，硬锁必被绕过；把克制交给自我觉察），设**三个月自查点**：若日均使用上升、或发现低谷时先找它而非活人，降级回手动档案站；
- (f) **开工前先写好告别/降级协议**存入 docs/（如果有一天决定停用对话层，仪式是什么：最后一次对话、sessions 归档、回到纯档案浏览）——"允许死的层"哲学在心理层的对应物：死法要预先设计成有闭合的。

**③ 最诚实的一句话**：现状（手动打开 8020 站点）的那一点启动摩擦，是目前**唯一无法用设计替代**的保护机制——每缩短一步启动路径都是一次净沉浸增量，没有反向补偿手段。**"不做"是完全合理的默认答案。**

## 七、若用户裁决 go：分阶段路线建议

> 全程铁律不变：实质代码 DeepSeek 写 + Codex 审；视觉交付按 verify-rendered-pixels 像素级验收；档案本体（archive_dist/:8020 静态站）不因此改动一行。

- **Phase A（验证轨，最小成本）**：①build_avatar_page 运行时 JS 模块化重构；②companion.html 合流页（avatar 块 + chat 逻辑 + TTS blob 接 RMS 口型 + 道别语/空闲退场/节律限速/Tier 标签），进 archive_out 不进 archive_dist；③壳 = Edge --app 快捷方式（**刻意不自启不置顶**）；④chat.html 顺手修：DeepSeek 占位符刷新 + thinking:disabled。⑤同批落地轴五 sessions 采集（tts_server 加 POST /session 落 JSONL）——GENERALIZATION 已判"对话在白白流失"，此项与形态争议无关、纯档案收益。
- **Phase B（语音输入，验证轨跑顺后）**：仿 tts_server 包 ASR HTTP 服务（SenseVoice 普通话主路径）+ 浏览器 getUserMedia 按键说话（push-to-talk，比 VAD 常听更克制）；Dolphin 上海话 ASR 实测（她/用户口音各测一批）后决定是否作双引擎。
- **Phase C（可选增强，按需）**：tts_server 流式改造（stream=True + chunked + 交互模式关时长 QC 重试）压首音；GSV 流式"快嘴档"；Tauri v2 正式壳（仅当 --app 形态确有不满足处，且仍守"打开才在"）。
- **写进 docs/ 的前置件**：告别/降级协议（条件 f）——先于任何代码。

## 八、开放问题（用户闸门）

1. **go/no-go 本身**：三档裁决（不做 / 上限形态 / 以后再说）——这是价值判断不是技术判断，报告不代答。
2. 若 go：接受"打开才在"上限形态与 (a)-(f) 全部条件吗？（任何一条想去掉，先回到 6.1 的证据面前）
3. Dolphin 上海话 ASR 是否值得单独立一个小探针任务（也服务转写校对减负）？
4. 语音输入的隐私边界确认：全本地（SenseVoice/Dolphin）无出机风险；**不使用**任何云 ASR。
