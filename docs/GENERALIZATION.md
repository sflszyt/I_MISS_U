> 2026-08-17 用户定调五个泛化方向后的设计文档。回答两类问题：①前三轴（对象/数据源/语音）如何在现有架构上落地；②后两轴（人格维度/持续对话）的**新设计**。

## 轴一：对象泛化（活人 · 逝者 · 各种关系 · 宠物）

现有基础：全部文字层工具 person-generic，关系特定内容集中在 `persona/relationship.json` + `prompts/` 参数化模板——**架构已就绪，缺的是模板族与伦理分支**。

### 1.1 对象类型矩阵

| 类型 | 与现状的差异 | 设计要点 |
|---|---|---|
| 逝者（已验证：mama） | 基准形态 | 防理想化三约束全套适用（arXiv 2603.01017） |
| **活人** | **伦理形态完全不同** | **同意闸门 G0**：建档前必须记录对象本人知情同意（skill 强制第一步，写入档案 meta）；数据最小化（对方隐私内容默认剔除面更大）；对话页横幅从"非本人模拟"升级为"经 TA 同意的数字分身"；持续数据可以真正持续（对象还在产生新素材——增量摄入成为主流程而非补丁） |
| 父母/祖辈 | relationship 模板 | 已验证（亲子）；祖孙加代际语言差异注记 |
| 爱人 | 模板 + 敏感面 | 亲密内容的敏感清理关卡阈值需单独校准；防依赖约束权重更高（丧偶场景依恋风险最大） |
| 子女 | 模板 + 时间轴特殊性 | 成长期 persona 分纪元几乎必需（5 岁和 15 岁是两个人格，见轴四） |
| 同事/朋友 | 轻量形态 | 数据量通常小——管道应支持"薄档案"降级（无语音训练、persona 简版、以照片+记忆卡为主） |
| **宠物** | **无文字语料** | 独立模板族：persona=行为习性描述（人工撰写+照片视频佐证）；"语音"=叫声原声收藏（不合成）；对话页降级为相册+时间线+记忆卡（不做拟人对话——一只会说话的狗违背档案真实性原则）；卡通形象管线完全复用 |

### 1.2 落地动作

- `people/<slug>/profile.json` 增加 `subject_type`（deceased/living/pet）与 `consent`（活人必填：日期+方式）字段，skill 按类型分支流程与模板
- prompts/ 从单一 `chat_system.zh.md` 扩为模板族：`chat_system.<relation>.zh.md`，共享六铁律骨架，参数化关系语气

## 轴二：数据源泛化（WhatsApp · Emails · IG · FB · 微博 · 照片视频）

现有基础：L1 源适配器架构（一源一 parser → UIF → 下游只消费 UIF）就是为此设计的。`schema/uif.schema.json` 已含 message/post/email/media_item 四类。

### 2.1 各源落地路径

| 源 | 获取方式 | parser 要点 |
|---|---|---|
| WhatsApp | 官方聊天导出（.txt/含媒体 zip）或 iOS/Android 备份 | 文本格式解析简单；媒体文件名关联；多语言时间戳格式族 |
| Emails | mbox/IMAP 导出（Gmail Takeout 等） | UIF email 类型已定义；thread 重建；附件入 media |
| Instagram/Facebook | **Meta 官方数据导出**（JSON zip，含私信/帖子/评论/照片） | 结构化好，parser 直读 JSON；IG story/FB 时间线映射 UIF post |
| 微博（#14 已立项） | 她本人账号导出 + 用户微博下她的评论 | UIF post + comments 字段已支持 |
| 微信朋友圈（#15 已立项） | 手机端"个人信息导出" | source=wechat_moments |
| 散装照片/视频 | 目录导入 | `ingest_media.py` 已有（EXIF 时间归位） |

### 2.2 新问题：多视角合并与去重

现状全部素材是单一视角（user 视角的微信）。泛化后必然出现：**多位家人各自贡献导出**（爸爸的微信里也有她、姐姐的 WhatsApp 里也有她）。

- UIF 信封已有 `viewpoint` 字段——每份贡献标注视角，天然支持
- **去重策略（需新建）**：同一对话可能出现在两台手机的导出里。方案：`dedup_key = hash(normalize(text) + timestamp±容差 + participants)`；重复记录保留一条、provenance 记录全部来源视角（"此话双方手机均有存证"反而是可信度加分）
- 多视角带来的珍贵增量：**她与不同人的对话**——轴四"关系分面"的数据基础

## 轴三：语音泛化（口音普通话 · 粤语 · 方言 · 英文）

现有基础：语音管线的**阶段是语言无关的**（选段→ASR→校对→切段→训练→评估→TTS 服务），语言特定的只有三个插槽：ASR 模型、TTS 底座、参考转写规范。

### 3.1 voice_profile 参数化（写入 profile.json）

```json
{
  "voice_profile": {
    "language": "wu | yue | cmn | en | ...",
    "asr": {"model": "u2pp_wenetspeech_wu", "decode_yaml": "..."},
    "tts_base": {"family": "cosyvoice2-wu-sft | funcosyvoice3 | ...", "path": "..."},
    "needs_sft": true,
    "domain_tags": {"native": "<|wuyu|>", "accented_mandarin": ""}
  }
}
```

### 3.2 选型矩阵（随生态演进维护）

| 目标语音 | 推荐路径 | 训练需求 |
|---|---|---|
| 标准普通话 | Fun-CosyVoice3 zero-shot（官方 CER 1.45%） | **免训练**——20 秒参考即可，管道大幅缩短 |
| **带口音普通话** | 本人数据 SFT（任意底座） | **双语域发现可迁移**：SFT 后裸文本输出=本人口音（mama 沪普实证）。这可能是本产品最独特的能力——市面 TTS 给你标准音，我们给你"她的口音" |
| 上海话/吴语 | CosyVoice2-Wu-SFT + SFT（已验证） | 短句强、长句受底座天花板压制 |
| 粤语 | CosyVoice3 系粤语支持 / 粤语开源底座调研 | 生态比吴语成熟，预期路径同吴语 |
| 其他方言 | 逐语言调研（底座存在性决定可行性） | 无底座的方言退化为"真声档案 + 免合成" |
| 英文 | 多底座可选（CosyVoice3 多语/XTTS 等） | zero-shot 大概率够用 |

原则不变：**尊重素材语言**（她说什么话就让她说什么话）、真声永远是档案核心、合成是短句增量能力、家人盲听是唯一验收标准。

## 轴四：人格维度扩展——persona/memory 之外还有什么让它"更像人"

现状盘点：persona.md（论断+证据+缺点面）、rhythm.json（交互节律）、memories.md（Tier-1 事件）、timeline、relationship.json（称呼/口头禅/方言表/禁忌话题）。这些回答了"她是谁、说话什么节奏、发生过什么"。**缺的维度，按数据可得性排序**：

### 4.1 时间性人格（persona_epochs）——最高优先

人不是一个扁平的人格。mama 的数据里就有清晰的分野：健康期的她 vs 患病后的她。现在 persona 是全时段压扁的平均像。

- 设计：`persona/epochs.json` 定义生命阶段边界（用户裁决 🚪），persona 论断挂 epoch 标签；digest/挖掘按 epoch 分桶
- 对话应用：检索可按纪元加权（默认加权"最像她自己"的纪元——用户选择哪个时期的她）；这对**子女建档**几乎是必需（5 岁与 15 岁）

### 4.2 关系分面（facets）——多视角数据到位后解锁

她对丈夫、对儿子、对老友是三副面孔（语气/话题/称呼全不同）。现有群聊数据已可初挖（她在家庭群 vs 亲友群的行为差异），多视角导入后完整成立。

- 设计：`persona/facets.json`：per-对象 称呼/语气特征/专属话题/典型互动模式；对话页可声明"以对儿子的面孔对话"（默认=建档者的关系）

### 4.3 叙事库（stories.md）——corpus 里现成可挖

人会反复讲同样的故事，每次略有出入——这是"像人"最强的信号之一。挖掘：跨年度找语义重复的叙事片段（她讲过 N 次的那件事），聚合成"她的保留曲目"，含每次讲述的差异。

- 对话应用：命中相关话题时，数字人讲的是**她真的讲过的故事、用她讲过的讲法**——而不是模型编排的复述。Tier-2 直引。

### 4.4 仪式历（rituals.json）——rhythm 的日历维度

rhythm 有时段习惯，缺**日历习惯**：生日必发的话、春节的规矩、冬至的汤圆、每年体检后的报平安。挖掘：按农历/公历节点聚类她的历年行为。

- 档案应用（不只是对话）：档案首页可以有"今天"——3 年前的今天她说了什么；她在这个节日惯常会说的话。**这让档案自己有了心跳，且完全不依赖生成**（纯检索，Tier-2）。

### 4.5 知识边界（knowledge boundary）——真实性的暗柱

她不知道 2024-02 之后的世界。数字人若谈论她死后发生的事，真实感瞬间崩塌（也是伦理问题）。

- 设计：profile.json 记 `data_cutoff`；chat 系统提示词注入"你不知道 X 之后的事，被问到就说不知道"；可选"知晓模式"开关（用户明确要求告诉她近况的对话形态——那是另一种真实：向她倾诉，而不是假装她知道）

### 4.6 感官签名（低成本高感）

表情包库（微信数据里就有她常用的 sticker，提取进档案，对话页可用**她真的用过的表情包**回复）、错别字与语气词习惯（rhythm 扩展：她把X打成Y的习惯性错字）、照片审美（她拍的照片 vs 别人拍她）。

### 4.7 明确不做

- 情绪状态机/"今天心情"模拟——纯生成、不可溯源、违背 Tier 纪律
- 主动发消息——沉浸度红线（arXiv 依据的依赖风险核心）

## 轴五：持续对话写回架构——最重要的新设计

**问题**：用户会持续与数字人对话，产生新的交流与故事。这些如何进入档案，又不污染她的真实性？

### 5.1 第一原则：两个纪元，永不合流

```
第一纪元（她活着时的真实数据）          第二纪元（她离开后的对话）
people/<slug>/raw+normalized          people/<slug>/sessions/
· 不可变、只读                         · 持续追加
· Tier-1/2                            · 用户话语 = Tier-2（用户视角的真实续写）
                                      · 数字人话语 = 永久 Tier-3（无论多动人）
        ↓                                     ↓
   memories.md（她的记忆）              sessions_memories.md（与数字妈妈的对话记忆）
        └────────── 永久分列，档案中明确分区 ──────────┘
```

数字人说过的话**永远不能**变成"她说过的话"。但用户对她说的话是真实的——那是用户哀伤旅程的记录，本身就是档案该收藏的东西（"那年冬天我告诉了她我升职的消息"是真事，即使听的人是模拟的）。

### 5.2 数据流设计

1. **采集**：chat.html 每轮对话落地 session 记录 `{ts, role: user|simulacrum, text, provider, model, retrieval_used[]}`。双通道：
   - 本地服务在（`session_collector`，可并入 tts_server 加 `POST /session` 端点）→ 自动写 `sessions/YYYY-MM/session_<id>.jsonl`
   - 服务不在（纯静态档案场景）→ localStorage 持久化 + 页面提供"导出对话"下载 JSONL（用户手动放回 sessions/）
2. **摄入**：`tools/ingest_sessions.py`（构建端）：校验/去重/敏感扫描 → sessions 层规范化
3. **记忆升级闸门** 🚪：对话页每条消息长按增加"记下来"→ 标记进 session 候选 → 闸门页裁决 → 升入 `sessions_memories.md`（**第二纪元记忆，独立文件，页面展示明确分区**："与数字妈妈的对话"）
4. **连续性检索**：sessions 成为第四检索源（`data/sessions.json`，标签 `[往次对话 · 数字对话记录]`）——数字人记得"上次你说工作很累"，连续感来自真实对话史而非人格漂移
5. **persona 永不自动更新**：对话不改变她是谁。唯一例外路径：用户在对话中回忆起**她生前的真事**（"我想起来她其实很怕打雷"）→ 走正常记忆闸门 → 可升入第一纪元 memories.md（这是用户提供的新证言，不是模型生成）

### 5.3 风险护栏（对齐 arXiv 2603.01017）

- 持续对话正是理想化与依赖风险的温床：sessions 摄入时同样跑敏感扫描 + 数字人话语永久 Tier-3 展示标签
- 不做：数字人主动发起对话/推送/定时问候（档案可以有"今天"节律卡——那是检索她的真话，不是它开口）
- 档案里保留使用统计的可见性（对话频次自见），把"沉浸度克制"交给用户自我觉察而非说教

### 5.4 与 20 年原则的相容性

sessions 层同样是 JSONL 开放格式；chat 页无服务时降级 localStorage+手动导出——**消费端仍然零依赖**。第二纪元的一切工具都在"允许死"的构建端。

## 落地优先级（并入 PIPELINE.md 12.4 的顺序）

1. skill 化基建（配置化/脚本收编）——不变
2. **轴五 sessions 架构**——用户已在真实使用对话页，对话正在白白流失，这是当下每天都在发生的数据损失 → 提前
3. 轴四低成本项：knowledge boundary（几行提示词）、仪式历"今天"卡（纯检索）、表情包提取
4. 轴四结构项：persona_epochs → stories.md → facets
5. 轴一/二/三随第二人物实战与新素材到达按需启动
